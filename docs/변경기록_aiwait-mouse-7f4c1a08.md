## 1. 판정 — 물음 1~4

### 물음 1. `Step2Concept` 에 마우스 취소를 어떻게 붙이는가

**판정: 공용 `AiWaitBar` 를 그대로 쓴다. 화면에 맞춰 바꾸는 것은 «자리» 뿐이고, 자리는 둘이다.**

근거 셋.

1. **바꾸지 않는 이유** — 사용자는 마법사 네 화면(`Step2Memo`·`Step3Synopsis`·
   `Step4Outline`·`Step5Treatment`)에서 이미 이 막대를 봤다. 같은 기다림에 다른 그림을
   내밀면 «그만두는 법»을 화면마다 새로 배워야 한다. 이 화면이 마법사 단계와 다른 것은
   **생김새(대화형 레이아웃)이지 기다림의 성질이 아니다.** 기다림은 똑같다 — 화면이
   멈추고, 몇 분이 걸리고, 사용자는 고장인지 아닌지 모른다.
2. **자리를 바꾸는 이유** — `AiWaitBar` 는 `style` prop 을 여백·너비 조정용으로 열어 두었다.
   그것이 화면별로 허용된 유일한 조정 축이다. 왼쪽 대화의 막대는 **입력칸 바로 위**에
   둔다. 사용자가 방금 「보내기」를 누른 자리이고, 손과 눈이 이미 거기 있다.
3. **막대가 «둘» 인 이유** — 이 화면에는 독립된 AI 호출이 둘 있다.
   `mainChat`(왼쪽 대화)과 `distillChat`(오른쪽 「정리해 보기」)이다. 둘은 동시에 돌 수
   있다. 막대가 하나면 「그만두기」가 **무엇을** 멈추는지 알 수 없다. 그래서 각 호출 옆에
   제 막대를 두고, 각 버튼은 제 옆의 호출만 멈춘다. 테스트가 이것을 못박는다
   (「정리 쪽만 멈추고 대화는 살아 있다」).

> **덧붙여 발견한 것 — 이 화면에는 «키보드 취소»도 사실상 없었다.**
> `Esc` 처리기가 `textarea` 의 `onKeyDown` 에만 붙어 있는데, 그 `textarea` 는
> `disabled={isStreaming}` 이다. 브라우저는 disabled 요소에 포커스를 주지 않는다.
> 즉 **답을 만드는 «동안» 에는 `Esc` 가 그 처리기에 닿을 수 없다.** F1 은 「마우스
> 사용자에게 취소가 없다」였지만, 실제로는 **아무에게도 없었다.**
> `Esc` 처리기는 **빼지 않고 그대로 두고**(지시서 금지선), 창 전체 `keydown` 경로를
> **더했다**. 같은 방식을 `SelectionPopover.tsx` 가 이미 쓰고 있다 — 새 체계가 아니다.
> (`jsdom` 은 disabled 요소에도 합성 키 이벤트를 전달하므로, 옛 경로만 두고 테스트를
> 짰다면 **초록인데 실제로는 동작하지 않는** 테스트가 됐을 것이다. E-026 그 자체다.)

### 물음 2. `ContinuityPanel` · `ResultPreviewModal` — 통일하는가

| 화면 | 판정 | 사용자가 «실제로» 잃고 있던 것 |
|---|---|---|
| `ContinuityPanel` | **통일한다** | 아래 셋 |
| `ResultPreviewModal` | **그대로 둔다** | **없다** |

**`ContinuityPanel` — 고친다.** 마우스로 누를 「취소」 버튼은 이미 있었다. 「일관성」은
이유가 못 된다는 지시대로, 잃고 있던 것만 적는다.

1. **살아 있다는 증거** — 이 점검은 **이 앱에서 가장 오래 걸리는 호출**이다(240초.
   다른 호출은 180초). 그 4분 동안 화면은 「편집자가 본문을 읽고 있습니다…」 한 줄에서
   멈춰 있었고, **10초가 지났는지 3분이 지났는지 알 방법이 없었다.** 멈춘 것과 일하는
   중을 구별할 수 없으면 사용자는 앱을 끈다.
2. **끝이 있다는 사실** — 「4분이 지나면 저절로 멈춥니다」를 **아무 데서도 말하지 않았다.**
   끝이 있는 기다림은 견딜 만하고, 끝이 없는 기다림은 견딜 수 없다.
3. **그만두는 법** — 같은 일에 이름이 둘이었다(여기는 「취소」, 마법사는 「그만두기」).

   덤으로, 한계 시간을 `CONTINUITY_TIMEOUT_SECS` 한 곳에서만 읽게 묶었다. 화면이
   「4분」이라 써 놓고 실제로는 다른 때에 멈추면 그게 새 거짓말이 된다.

**`ResultPreviewModal` — 그대로 둔다.** 기다리는 동안 이미 셋을 준다 — (1) 무슨 일인지
(액션 이름 + 「AI 가 분석 중」) (2) 살아 있다는 증거(0.25초마다 갱신되는 경과 시간)
(3) 마우스로 멈추는 버튼. **잃고 있는 기능이 없다.** 남은 차이 셋(경과 시간을 5초
뒤부터, 「언제 저절로 멈추는지」 한 줄, 버튼 이름)은 전부 **문면**이고, 전부
`StreamView.tsx` 안에 있다 — 이 발주가 못 쓰는 파일이다.

이 파일에서 할 수 있는 일은 `StreamView` **위에** 막대를 하나 더 얹는 것뿐인데,
그러면 한 창에 **멈추는 버튼이 둘**(「그만두기」·「취소」)이고 경과 시간이 둘이 된다.
컴퓨터 용어를 모르는 사용자에게 그것은 통일이 아니라 「어느 쪽이 진짜인가」라는 **새
물음**이다 — **지금보다 나빠진다.** 그래서 문면 한 줄도 바꾸지 않고 판정만 박아 두었다.

> 한 가지 더 — 여기의 「취소」는 마법사의 「그만두기」와 **뜻이 다르다.** `handleCancel`
> 은 호출을 멈추고 **창까지 닫는다**(`onComplete("discard")`). 마법사의 그만두기는
> 멈추기만 하고 화면은 남는다. 낱말만 같게 만들면 **같은 이름이 서로 다른 일을 하게
> 된다.** 통일하려면 이 차이를 먼저 정해야 한다. 이 사실도 파일에 박아 두었다.

### 물음 3. 낱말 세 갈래(「취소」·「중단」·「그만두기」)를 맞추는가 — 어디까지인가

**판정: 「지금 도는 AI를 멈춘다」는 뜻으로 사용자에게 보이는 낱말만, 이 발주가 쓸 수
있는 파일 안에서 「그만두기」로 맞춘다. 표식과 다른 뜻의 「취소」는 건드리지 않는다.**

절반만 바꾸는 위험을 이렇게 다뤘다 — **낱말을 «뜻» 으로 먼저 갈랐다.**

| 자리 | 지금 | 어떻게 했나 |
|---|---|---|
| `Step2Concept` 입력칸 안내 「Esc 중단」 | 중단 | 없앴다. 대신 만드는 «동안»에만 「Esc 를 눌러도 그만둘 수 있습니다」가 뜬다 — 안내를 뺀 게 아니라 **닿는 자리로 옮겼다** |
| `Step2Concept` 상태줄 「AI가 답변 중… (Esc 로 중단)」 | 중단 | 위와 같음. 「무슨 일 중인지」는 이제 대기 막대가 말한다 |
| `ContinuityPanel` 버튼 「취소」 | 취소 | `AiWaitBar` 로 대체 → 「그만두기」 |
| `ContinuityPanel` 알림 「점검을 취소했습니다」 | 취소 | 「점검을 그만뒀습니다」 |
| **`aiBridge` 의 `"사용자가 취소했습니다."`** | 취소 | **건드리지 않는다.** 이것은 화면 문면이 아니라 **기계 표식**이다 — `isUserStopped()` 가 이걸 보고 「그만둠」과 「고장」을 가른다. 여기까지 바꾸면 **다섯 화면 전부에서** 사용자가 스스로 멈춘 자리에 **빨간 오류가 뜬다.** 게다가 이 발주가 못 쓰는 파일이다 |
| `StreamView.tsx` 버튼 「취소」 | 취소 | **못 건드린다**(발주 범위 밖). 아래 8절에 보고 |
| `WizardOverlay`·`ConceptWizard`·`NewProjectModal` 의 「취소」 | 취소 | **건드리지 않는다.** 뜻이 다르다 — 「AI를 멈춘다」가 아니라 「이 작업/창을 접는다」이다. 이걸 「그만두기」로 바꾸면 **다른 두 일이 같은 이름을 갖게 되어 지금보다 나빠진다** |

**남은 어긋남은 하나다** — `StreamView` 를 쓰는 팝오버 결과 창의 「취소」 버튼. 셋에서
둘로 줄었고, 남은 하나는 **한 파일의 한 줄**이며 위치를 8절에 적어 두었다. 이 발주가
그걸 반만 고칠 수 없어서 **아예 손대지 않았다** — 반만 고치면 같은 창 안에서 어긋난다.

테스트는 **그 파일의 글자를 못박지 않는다.** 못박는 것은 `isUserStopped()` 판별이
통한다는 사실 하나다. 표식을 어떻게 싣는지(문자열이냐 종류냐)는 지금 다른 발주가 고치는
중이고, 그 판단을 내 테스트가 막아서는 안 된다.

### 물음 4. 타자기 커서 「▍」 를 어떻게 하는가

**판정: 없앤다. 그 자리에 남는 것을 화면마다 정해 두었다.**

근거 — codex 는 글자를 한 자씩 주지 않는다. 본문은 턴이 끝난 뒤 통째로 온다. **한
글자도 오지 않는 자리에서 커서만 깜빡이는 것은 「지금 타자 치는 중」이라는 거짓말**이고,
3분이 지나도 화면은 똑같다. 「살아 있음」을 알리는 척하면서 실제로는 아무것도 알리지
않는다.

| 자리 | 없앤 뒤 그 자리에 남는 것 |
|---|---|
| `Step2Concept` 대화 말풍선 | **대기 막대**(무슨 일 · 몇 초째 · 언제 저절로 멈추는지 · 그만두기). 말풍선 자체는 **실제로 온 것이 있을 때만** 띄운다 — 빈 말풍선은 「AI 코치가 아무 말도 하지 않았다」로 읽힌다 |
| `Step2Concept` 오른쪽 정리 영역 | 대기 막대. 그리고 정리하는 «중»에는 「정리해 보기를 눌러주세요」를 **띄우지 않는다** — 지금 하고 있는 일을 누르라고 하는 꼴이었다 |
| `Step3Synopsis` 본문 상자 | **상자는 남긴다**(글이 어디에 나타날지 미리 보여야 도착했을 때 화면이 튀지 않는다). 그 안에 흐린 한 줄 — **「여기에 시놉시스가 나타납니다.」** 빈 상자만 남기지 않았다 |

## 3. 화면 문면 실물 — 사용자가 실제로 보는 글자 그대로

아래 **컨셉 대화 화면** 문면은 **실제로 렌더한 DOM 에서 그대로 뽑은 것**이다(추정 아님).
**연속성 감시자**·**시놉시스** 문면은 같은 부품(`AiWaitBar`)에 `limitSecs=240` 을 준
결과와 소스 문자열에서 옮긴 것이다 — 「4분이 지나면 저절로 멈춥니다」는 기존
`aiWaitBar.test.ts` 가 이미 단언하고 있다.

**컨셉 대화 화면 — AI 가 답을 만드는 동안 (12초 경과 시점, 입력칸 바로 위)**

```
● AI 코치가 답을 쓰고 있습니다
  12초째 기다리는 중 · 3분이 지나면 저절로 멈춥니다        [ 그만두기 ]
```

처음 5초 동안은 숫자 대신 이렇게 뜬다.

```
● AI 코치가 답을 쓰고 있습니다
  잠시만 기다려 주세요. 길면 몇 분 걸립니다.               [ 그만두기 ]
```

**입력칸 안내**

- 입력칸 placeholder: `답변을 입력하세요. (Cmd/Ctrl+Enter 로 전송)`
- 만드는 동안 상태줄: `Esc 를 눌러도 그만둘 수 있습니다`
- 평소 상태줄: `Cmd/Ctrl + Enter 로 전송`

**오른쪽 「정리해 보기」가 도는 동안**

```
AI 가 정리한 컨셉 단락
● 컨셉 단락을 정리하고 있습니다
  잠시만 기다려 주세요. 길면 몇 분 걸립니다.               [ 그만두기 ]
```
(그 아래 「아직 정리된 컨셉이 없습니다…」 안내는 이때 **뜨지 않는다**)

**그만두기를 누른 뒤**

```
AI를 그만뒀습니다. 쓰시던 내용은 그대로 있습니다 — 언제든 다시 시작할 수 있습니다.
```
(빨간 오류 배너는 뜨지 않는다)

**연속성 감시자 — 점검하는 동안**

```
[ 점검 중… ]
● 편집자가 본문을 읽고 있습니다
  12초째 기다리는 중 · 4분이 지나면 저절로 멈춥니다        [ 그만두기 ]
```
그만두면 알림: `연속성 점검을 그만뒀습니다.`

**시놉시스 화면 — 아직 아무것도 오지 않았을 때 (커서 자리)**

```
┌────────────────────────────────────┐
│ 여기에 시놉시스가 나타납니다.       │
└────────────────────────────────────┘
```

## 4. C1 — 마우스 취소·Esc 취소를 각각 어떻게 증명했나

새 파일 `packages/obsidian-plugin/tests/studio/wizard/aiWaitMouse.test.ts` (23 테스트).
**진짜 `Step2Concept`** 을 **진짜 DOM** 에 그린다. 가짜는 CLI 를 부르는 경계와 디스크뿐이고,
**취소 배선(`useStreamingChat` → `AbortController` → `AiWaitBar`)은 전부 진짜**다.

**마우스 취소** — 「버튼이 렌더된다」를 보지 않는다. 보는 것은 **신호**다.

1. 마운트 → 호출이 실제로 시작된다(`startedSignals[0].aborted === false`).
2. 「그만두기」에 **진짜 `MouseEvent("click")`** 을 던진다.
3. **진행 중이던 호출의 `AbortSignal` 이 실제로 `aborted === true` 가 된다.**
4. **키보드를 한 번도 쓰지 않았음을 세어서 증명한다** — `window` 에 `keydown`/`keyup`/
   `keypress` 계수기를 달고 `keyEventCount === 0` 을 단언한다.
5. 그 뒤 빨간 오류 배너가 **없고**, 「쓰시던 내용은 그대로 있습니다」가 **뜬다**.
6. 대조군 — **누르지 않으면 `aborted === false`** 다(끊은 원인이 그 버튼임을 확인).

**Esc 취소** — 같은 파일에서 함께 못박았다.

1. `document.body` 에 진짜 `KeyboardEvent("keydown", {key:"Escape"})` 를 던진다(포커스가
   갈 수 있는 실제 자리에서 창까지 버블링한다).
2. 같은 `AbortSignal` 이 `aborted === true` 가 된다.
3. **옛 경로가 왜 닿지 못했는지도 못박았다** — 만드는 동안 `concept-input` 이
   `disabled === true` 이고 `document.activeElement` 가 그 입력칸이 **아님**을 단언한다.
4. 옛 `Esc` 처리기가 **삭제되지 않았음**을 소스 계약으로 단언한다
   (`e.key === "Escape" && mainChat.isStreaming` 이 그대로 있다).
5. 아무것도 돌지 않을 때 `Esc` 는 새 호출을 만들지도, 무엇을 깨뜨리지도 않는다.

**막대가 둘인 판정도 행동으로 증명했다** — 대화와 정리를 동시에 돌린 뒤 정리 쪽
「그만두기」만 누르면 `startedSignals[1].aborted === true`, `startedSignals[0].aborted
=== false` 다. 각 버튼이 제 옆의 호출만 멈춘다.

**하나 있다 — 「대기 표시」와 「진행 알림」이 서로 모르는 채로 같은 자리를 놓고 다툰다.**

옳다(그 발주 주석이 근거를 잘 적어 두었다). 그런데 이제 **같은 사실을 두 곳이 말한다** —

`[AI 진행]` 이라는 **대괄호 표식**을 붙여 본문과 구별해야 했다. 표식은 컴퓨터 용어는
아니지만 사용자가 읽을 글도 아니다.

지금 구조가 이미 답을 갖고 있다 — **진행 소식은 본문 자리가 아니라 대기 막대의 label
자리로 가야 한다.** `AiWaitBar` 는 `label` 을 이미 받고 있으므로, 「무슨 일 중인지」를
호출자가 실시간으로 갈아끼울 수 있게 하면 `[AI 진행]` 줄은 본문에서 사라지고 대괄호
표식도 필요 없어진다.

```
● 자료를 확인하는 중입니다        ← 진행 소식이 여기로
  12초째 기다리는 중 · 3분이 지나면 저절로 멈춥니다     [ 그만두기 ]
```

**이 발주에서는 하지 않았다** — `AiWaitBar.tsx` 와 `streamingChat.ts` 둘 다 다른 발주가
지금 쓰는 자리이고, 「고쳐야 풀린다면 고치지 말고 보고하라」는 지시가 있다. **두 발주가
끝난 뒤 한 번에 볼 문제**로 올린다.

## 과제 A — 「아무것도 안 눌렀는데 «사용자가 취소했습니다»」 (C12~C16)

### 원인 판정 — 세 후보를 어떻게 갈랐나

| 후보 | 판정 | 어떻게 갈랐나 |
|---|---|---|
| 전역 `activeAbortController` 를 덮어쓰는 것이 «증폭기» | **맞다 — 그러나 그것만이 아니다** | `wizardStore.ts` 가 `activeAbortController = ctrl` 로 앞 controller 를 **abort 하지도 기억하지도 않고** 참조만 버린다. 주인을 잃은 요청은 계속 살아 있다가, 이후 어떤 경로든 abort 를 걸면 끊긴다 |
| `cancelStream()` 이 내부 전환에서도 불린다 | **결정적 방아쇠 — 확인** | `completeCurrentStage()`·`revisitStage()` 가 진행 중 요청을 `cancelStream()` 으로 끊는다. 그런데 `cancelStream()` 은 «사용자가 그만뒀다» 는 뜻으로 쓰이는 자리(WizardChat 의 Esc)와 **같은 함수**다. 그래서 내부 전환이 곧바로 「사용자가 취소했습니다」가 됐다. **중복 호출이 없어도 이것만으로 증상이 난다** |
| `CLIWizardBridge` 의 재시도 루프 | **오류 세 줄의 정체 — 확인** | `for (attempt < 2)` 가 «끊김» 도 재시도한다. 같은 `opts.signal` 을 다시 넘기므로 두 번째도 즉시 취소된다. 그래서 「첫 시도 실패 … 재시도합니다」 → 「CLI 호출 실패 …」 → 「AI 응답 실패 …」 **정확히 세 줄**이 쌓였다 |

**가려내지 못한 것 하나** — 「무엇이 호출을 두 번 태웠는가」는 **정적 읽기만으로 특정하지 못했다.**
같은 질문이 두 번 붙으려면 같은 engine 위에서 `runAskAndStream` 이 두 번 완주해야 하는데,
도달 가능한 경로(`sendUserMessage`·`completeCurrentStage`·`revisitStage`·`regenerateLast`)
중 어느 것이 실제로 두 번 발화했는지는 실행 로그 없이 단정할 수 없다.
**그래서 방아쇠를 찾는 대신 «어느 방아쇠가 당겨져도 해롭지 않게» 층을 닫았다** —
겹치면 앞 요청을 명시적으로 밀어내고, 밀려난 요청의 답은 화면에 붙지 못하며,
밀려난 끊김은 오류로 보이지 않는다.

### 「전역이라서 문제」인가 — 컨셉 마법사 방식으로 옮겨야 하는가

**아니다. 소유자는 스토어가 맞다.** 근거 —
컨셉 마법사의 호출은 «컴포넌트» 가 소유한다(`useStreamingChat` 의 `useRef`). 반면 기획
인터뷰의 `start()` 는 **`Step5Commit` 과 전역 단축키에서** 시작되고, 나머지도 스토어 액션이
시작한다. 어느 것도 특정 컴포넌트의 수명에 매여 있지 않다. 훅으로 옮기면 컴포넌트 밖에서
시작되는 `start()` 가 갈 곳을 잃는다.
**결함은 「전역이라서」가 아니라 「주인이 바뀔 때 앞 주인을 말없이 버려서」다.**
그래서 전역은 유지하고 **소유권 이전을 명시적으로** 만들었다(`supersedeActiveAsk()`).

### 무엇을 고쳤나

1. **`runAskAndStream` 을 한 번에 하나로.** 새 요청은 앞 요청을 명시적으로 abort 하고
   일련번호(`askSeq`)로 «지금 유효한 요청» 을 가린다. 밀려난 요청의 답이 늦게 도착해도
   화면에 붙지 않는다(`if (superseded()) return;`).
2. **끊김을 세 갈래로 갈랐다** — ① 사용자가 그만뒀다(담담한 안내) ② 새 요청이 밀어냈다
   (감춘다) ③ 진짜 실패(오류). 판단 기준은 «문면» 이 아니라 «누가 끊었는가» 라는 사실이다.
   문면으로 가르면 문면이 바뀌는 날 조용히 깨진다.
3. **내부 전환은 `cancelStream()` 을 쓰지 않는다.** `completeCurrentStage`·`revisitStage`·
   `sendUserMessage` 는 `supersedeActiveAsk()` 를 쓴다. `cancelStream()` 은 이제 오직
   «사용자가 그만두라고 했다» 만 뜻한다.
4. **끊긴 호출은 재시도하지 않는다.** `CLIWizardBridge` 가 `readAiFailureKind(e) === "canceled"`
   (병행 발주가 만든 종류 체계) 또는 `signal.aborted` 이면 조용히 그대로 올려 보낸다.
   보여줄지 말지는 «끊긴 이유를 아는» 스토어가 정한다.

### 물음 3 — 자동 취소를 사용자에게 보여야 하는가

**아니다.** 뒤 요청이 화면을 이어받으므로 앞 요청의 끊김은 사용자가 알 필요 없는 내부
사정이다. 대기 표시조차 건드리지 않는다(껐다 켜면 화면이 깜빡인다). 다만 **사용자가 직접
Esc 로 그만둔 경우는 감추지 않는다** — 자기가 한 일에 아무 반응이 없으면 그것도 고장이다.

### 물음 4 — 원인별 안내

**갈랐다.** 전에는 원인이 무엇이든 「다른 모델(예: `-m gpt-5-codex`)을 지정해보세요」라고
했다. 원인이 «취소» 인데 모델을 의심하게 만드는 오진이고, 게다가 `gpt-5-codex` 는 이
카탈로그에 없는 낡은 이름이다. 이제 실패 «종류» 별로 다른 한 마디를 붙이고(시간 초과 /
빈 답 / 실행 실패 / 종료 코드), **종류를 모르면 아무 말도 붙이지 않는다** — 틀린 안내는
없느니만 못하다.

### 함께 고친 것 — [답변] 버튼이 «안 보이던» 이유

코드에도 CSS 에도 있는데 화면에 없었다. 원인은 **스크롤**이다.
「직접 입력」을 고르면 답변칸과 [답변] 버튼이 대화 흐름(`.wizard-thread`, `overflow-y:auto`)
**아래쪽에 새로 펼쳐지는데**, 자동 스크롤의 의존값이 `[messages.length, streamingBuffer,
isStreaming]` 뿐이라 그 펼침을 따라가지 않았다. 버튼은 **화면 밖**에 있었다.
`selectedChoice`·`otherDraft` 를 의존값에 더해 펼쳐진 자리로 스크롤이 따라가게 했다.

> **한계 — 밝힌다.** macOS 옵시디언 실물에서 재현·확인하지 못했다(이 작업 범위에 배포가
> 없다). 그래서 «보인다» 를 세 갈래로 나눠 잡았다 — (a) DOM 에 실제로 있다 (b) 글자를
> 넣으면 실제로 눌리는 상태가 된다 (c) 진짜 클릭이 실제로 답을 보낸다. 이 셋은 테스트로
> 고정했고, (d) «화면 안에 있다» 는 스크롤 의존값 계약으로 고정했다. CSS 는 손대지 않았다
> — `--color-accent` 는 `:root` 에 정의돼 있어 옵시디언에서도 풀린다(색 문제 아님).

## 과제 B — 한글로 쓰면 `Cmd+Enter` 전송이 안 된다 (C6·C7)

### 원인 판정 — 세 후보를 어떻게 갈랐나

| 후보 | 판정 | 어떻게 갈랐나 |
|---|---|---|
| 1. 한글 IME 조합 중 키 이벤트가 다르게 온다 | **원인 확정** | **재현으로 갈랐다.** 옛 코드(`e.key === "Enter"`)에 조합 중 이벤트(`key:"Process"`·`keyCode:229`·`isComposing:true`·`metaKey:true`)를 실제 DOM 으로 보내면 **전송이 안 된다.** 같은 옛 코드에 조합이 아닌 이벤트를 보내면 **잘 된다.** 즉 옛 코드는 영문에서만 동작했다 — 대표가 한글을 쓰신다는 사실과 정확히 맞는다 |
| 2. 옵시디언이 `Cmd+Enter` 를 가로챈다 | **아니다** | ① 이 앱의 전역 단축키(`shortcuts.ts`)에는 **Enter 분기가 없다**(`1/2/3/k/n/,` 뿐) ② 플러그인은 `hotkeys:` 를 하나도 등록하지 않는다 ③ 구조상 불가능하다 — React 18 은 마운트 컨테이너(`ManuscriptStudioView` 의 `host`)에 리스너를 단다. 그것은 `document` 의 **자손**이므로 버블링에서 **옵시디언의 document 리스너보다 먼저** 돈다. 게다가 `Cmd+K`·`Cmd+S` 같은 window 단축키가 실제로 동작한다는 것은 옵시디언이 Cmd 조합의 전파를 끊지 않는다는 뜻이다 |
| 3. 포커스가 textarea 에 없다 | **아니다** | 증상 자체가 배제한다. 대표가 친 한글이 입력칸에 들어갔고 [보내기] 를 누르면 **그 글이 전송된다** → 키 입력이 그 textarea 에 닿았다 → 포커스가 있었다. 그리고 **앞 발주에서 찾은 `disabled={isStreaming}` 과는 다른 상황이다** — 전송은 «답을 만들기 전» 이라 입력칸이 꺼져 있지 않다(테스트로 `ta.disabled === false` 를 확인) |

### 무엇을 고쳤나

판별 축을 `key`(IME 가 바꿔치는 «논리» 값)에서 **`code`(IME 와 무관한 «물리» 키)** 로 옮겼다.
`e.key === "Enter"` 비교도 **남겨 두었다 — 더하되 빼지 않는다.**

```
before:  if ((e.metaKey || e.ctrlKey) && e.key === "Enter")
after :  if ((e.metaKey || e.ctrlKey) && isEnterKey(e))
         isEnterKey = e.key === "Enter" || e.code === "Enter" || e.code === "NumpadEnter"
```

**왜 「조합 중이면 무시」가 아니라 「조합 중에도 보낸다」인가.** 흔한 IME 방어는 「조합 중
Enter 무시」인데, 그것은 **맨 Enter 로 전송하는** 화면의 규칙이다 — 거기서 Enter 는 「음절
확정」과 「전송」 둘 다를 뜻해 모호하다. 여기는 `Cmd/Ctrl+Enter` 라 모호하지 않다.
**한글 IME 는 Cmd+Enter 를 음절 확정에 쓰지 않는다.** 누른 사람의 뜻은 하나뿐이다.

**마지막 글자를 잃지 않게** 전송할 때 React 상태(`draft`)가 아니라 **입력칸에 지금 실제로
있는 글자**(`e.currentTarget.value`)를 쓴다. 조합 중에는 상태가 마지막 음절만큼 뒤처질 수
있는데, 사용자가 보내려는 것은 «지금 눈에 보이는 문장» 이지 한 글자 모자란 문장이 아니다.

**두 화면 모두 고쳤다** — `Step2Concept.tsx`(대표가 겪은 화면)와 `WizardChat.tsx`(글자
그대로 같은 코드). 공용 파일을 새로 만들 수 없어 같은 함수를 양쪽에 두었고, 둘이 갈라지지
못하도록 테스트가 **양쪽을 함께** 못박는다.

### C7 — 화면 안내와 실제 동작

화면은 「Cmd/Ctrl+Enter 로 전송」이라 적혀 있었다. **적힌 대로 되게 했다** — 문면은 그대로
두고 동작을 맞췄다. 테스트가 「적힌 문면이 있다」와 「그 약속이 한글 조합 중에도 지켜진다」를
**한 테스트 안에서** 함께 확인한다.

## 과제 C — 「다시 다듬기」가 글을 나쁘게 만든다 (C9~C11)

### 판정 1 — 첫 생성과 다듬기를 어떻게 가르나

**빌더는 하나로 두고 안에서 가른다. 역할(system) 프롬프트는 둘로 가른다.**
근거 — 두 일은 재료(컨셉 단락·메모 단서·노트)를 공유하므로 조립을 쪼개면 갈라진다.
반면 «짓는 일» 과 «고치는 일» 은 역할이 다르므로 system 프롬프트는 갈라야 한다.
**결정적 근거**: 빌더를 둘로 쪼개면 실패 양상이 「어느 함수를 부를지 틀림」이 되는데,
이 결함이 정확히 그 종류(재제안 경로만 인자를 빠뜨림)였다. 하나로 두면 실패 양상은
「인자를 안 넘김」 하나뿐이고, 그것은 테스트로 못박기 쉽다.

**발주자 제약과 갈린 지점 — 밝힌다.** 대표 지시로 「프롬프트를 제대로 설계하라」가
채택됐지만, 나는 **첫 생성 프롬프트를 일부러 손대지 않았다.** 그 경로는 대표가 지금 쓰고
계신 결과물을 내고 있고 이번 결함은 그 경로의 문제가 아니다. 검증 없이 함께 바꾸면 지금
멀쩡한 것까지 나빠질 수 있다. **재설계는 「다듬기」 경로에만 했다.**

### 판정 2 — 손으로 고친 내용도 대상인가

**대상이다. 그리고 지금 코드는 둘을 구별하지 않는다 — 확인했다.**
`session.synopsis` 는 AI 완료 시에도(`setSynopsis(fullText)`), 작가가 textarea 를 고칠
때에도(`onChange={(e) => setSynopsis(...)}`) **같은 필드**에 쓰인다. 즉 「AI 가 쓴 마지막
판」과 「작가가 손댄 판」은 코드상 구별되지 않는다.
**구별하지 않는 편이 옳다.** 작가가 다듬어 달라는 것은 «지금 눈에 보이는 글» 이고,
손댄 것을 되돌리면 작업을 빼앗는 셈이다. 역할 프롬프트에도 「작가가 직접 고친 흔적은
의도로 보고 존중하라 · 되돌리지 마라」를 명시했다.

### 판정 3 — 추가 지시 없이 눌렀을 때

**누르게 두되, 크게 바꾸지 말라고 이른다.** 버튼을 막는 것은 정당한 요청(「한 번 더
다듬어 줘」)을 벌하는 것이고, 아무 일도 안 하는 것은 고장으로 보인다. 대신 프롬프트가
「따로 지시가 없으니 실제로 약한 곳만 손보고 나머지는 그대로 두라」고 한다 —
**실패 양상이 「나쁘게 새로 씀」에서 「거의 안 바뀜」으로 옮겨간다.**

### 판정 4 — 버튼 이름

「다시 다듬기 (재제안)」 → **「이 글 다듬기」**(글이 있을 때) / **「시놉시스 만들기」**(없을 때).
「재제안」은 «새로 제안한다» 는 뜻이라 **옛 (잘못된) 동작의 이름**이었다. 이름이 하는 일과
어긋난 채 두지 않는다.

### 프롬프트 — 바꾸기 전 / 바꾼 뒤

**바꾸기 전** (다듬기 경로가 내던 것 — 기존 글이 어디에도 없다)

```
## 컨셉 단락
{컨셉}

## 추가 지시
{지시}

위 컨셉으로 시놉시스를 작성하세요.
```
역할 프롬프트: `당신은 책의 시놉시스를 짓는 편집자입니다. …` (첫 생성과 **동일**)

**바꾼 뒤** (다듬기 경로)

```
## 컨셉 단락
{컨셉}

## 지금 시놉시스 (다듬을 대상)
{지금 화면에 있는 글}

## 추가 지시
{지시}

「지금 시놉시스」를 「추가 지시」대로 다듬어 주세요. 지시가 닿지 않는 문장은 그대로 두세요.
```
지시가 없으면 마지막 줄이 바뀐다 — `「지금 시놉시스」를 다듬어 주세요. 따로 지시가 없으니
실제로 약한 곳만 손보고, 나머지는 그대로 두세요.`
첫 생성 경로는 **문면 그대로** 유지된다(`위 컨셉으로 시놉시스를 작성하세요.`).

역할 프롬프트는 새로 썼다(`SYNOPSIS_REFINE_SYSTEM_PROMPT`) — 역할을 «고쳐 주는 편집자» 로
못박고, 판단 항목 넷을 주고, 출력 계약을 건다.

### 「고민해서 쓰도록」을 무엇으로 구현했나

**즉답을 막는 방법으로 «판단 의제» 를 줬다** — 「잘 생각해봐」 한 줄이 아니라, 쓰기 전에
스스로 정할 것 넷을 열거한다.

- 지시가 지금 글의 **어디를** 겨냥하는가 / 실제로 바뀌어야 할 문장은 어느 것인가
- 반드시 **살려야 할 것**은 무엇인가 (톤·은유·고유 표현·작가가 손댄 대목)
- 한 곳을 고치면 **앞뒤가 어긋나지 않는가**, 어긋나면 어디까지 함께 손보는가
- 지시와 **무관한 문장은 왜 그대로 두어야** 하는가

모델 지능을 낮게 잡는 장치(형식 강제·예시 나열·기계적 체크리스트)는 넣지 않았다.
넷은 «출력 형식» 이 아니라 «정해야 할 것» 의 목록이다.

**화면을 더럽히지 않는 보장 셋.**
① 「이 판단은 속으로만 하세요. 판단한 내용을 글에 쓰지 마세요.」를 의제 바로 뒤에 둔다.
② 출력 계약을 **마지막 줄**에 다시 둔다(가장 잘 지켜지는 자리) — 「출력은 다듬어진
시놉시스 본문 한 단락뿐입니다. 머리말·맺음말·무엇을 왜 바꿨는지에 대한 설명·변경 요약·
헤더·번호·볼드를 붙이지 마세요.」
③ 마지막에 **무엇을 받는 사람인지** 못박는다 — 「작가가 받는 것은 글이지 보고서가 아닙니다.」

이 방식은 이 코드베이스에서 **이미 작동이 확인된 기제**다 — 첫 생성 프롬프트의
「헤더/번호/볼드 없이 단락 하나만 출력」이 같은 계약이고 지금 잘 지켜지고 있다.
새 파싱 장치나 후처리를 만들지 않았다(그랬다면 스트리밍 화면에 사고 과정이 그대로
번쩍였을 것이다 — codex 는 본문을 턴 끝에 통째로 준다).

> **한계 — 밝힌다.** 단위 테스트는 **프롬프트에 그 계약이 실려 있음**을 고정할 수 있을
> 뿐, **모델이 그것을 지킨다**는 것을 보장하지 못한다. 실제 출력 품질은 대표가 쓰시면서
> 확인해야 하는 영역이다.
